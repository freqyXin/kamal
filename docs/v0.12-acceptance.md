# K'amal v0.12 integration and acceptance

`kamal-accept-v012` is the release gate between the v0.12 architecture work and
hardware-in-the-loop BLE validation. It uses an injected synthetic backend and
**does not open a BLE adapter, transmit RF, or use the network**.

The acceptance workflow exercises the cross-component chain rather than testing
one module in isolation:

1. create an explicit synthetic authorization scope and exact-byte operation request;
2. build a hash-bound GATT operation plan;
3. execute read/write operations through a synthetic backend while exercising the persistent safety interlock;
4. verify immutable incremental execution artifacts and conservative result/effect semantics;
5. create an offline, SHA-256-bound analyst review artifact;
6. build a valid active-GATT evidence report and assessment;
7. enrich that assessment with a local synthetic device-context catalog;
8. produce a BSAM mapping without pass/fail inference; and
9. run negative fail-closed gates for expired authorization, target mismatch, corrupt plans, unsafe latches, partial failures, uncertain cleanup, connection loss, and artifact overwrite attempts.

The acceptance report records SHA-256 and byte size for every intermediate
artifact. Hash bindings are checked across authorization -> plan, request ->
plan, operation -> review, evidence -> assessment, and assessment -> enrichment.

## Semantic acceptance requirements

A successful GATT write is accepted only as a transport/client-API and
protocol-visible outcome. The executor must leave application acknowledgement,
state change, and security effect as `not_assessed`. Higher-level conclusions
remain separate reviewer actions.

BSAM evidence coverage must not be promoted into a pass/fail conclusion. The
synthetic write-without-response metadata intentionally produces a review
candidate for service access control, demonstrating that candidate concerns are
preserved without becoming confirmed findings or BSAM failures.

## Safety acceptance requirements

The release gate verifies that:

- an existing unsafe latch blocks a later run before the synthetic discovery boundary;
- an orphaned/stale `active-run.json` lease also blocks a later run before discovery;
- ordinary operation failure preserves partial evidence and clears the lease when disconnect is confirmed safe;
- uncertain disconnect persists `unsafe-stop.json` and requires recovery;
- connection loss stops remaining operations rather than reconnecting and continuing; and
- immutable JSON artifacts are never silently overwritten.

The harness also statically checks offline assessment/intelligence/planning
modules for direct imports of common BLE/network execution dependencies. This is
an architectural guardrail, not a proof against every possible future side
effect, so code review remains required.

## Running the gate

Use a new work directory and a new report path:

```bash
bin/kamal-accept-v012 \
  --work-dir /tmp/kamal-v012-acceptance-work \
  --json /tmp/kamal-v012-acceptance.json
```

Both paths are create-only. Reusing either path fails closed.

## Hardware acceptance after this gate

A green synthetic gate does **not** validate BlueZ, the Linux adapter, the RF
environment, target behavior, or hardware cleanup semantics. The first hardware
acceptance must therefore use an owned or expressly authorized target and a
read-only GATT plan. Write acceptance comes only after read-only connection,
evidence persistence, disconnect, and safety-state cleanup have all been
observed on hardware.

The v0.12 assessment path consumes active-GATT enumeration reports. Executor operation results and analyst effect reviews remain separately hash-bound artifacts; this acceptance gate does not silently transform those artifacts into assessment observations.

For a hardware run, retain the authorization, request, plan, `run-start.json`,
each `operation-NNN.json`, `run-final.json`, safety-state artifacts, and any
offline review artifacts as one evidence set.
